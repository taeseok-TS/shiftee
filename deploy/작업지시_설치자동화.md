# 작업 지시 — 고객사 설치 자동화 마무리

> 지시일 2026-08-13 · 요청: 디렉터
> 이 문서 하나만 읽고 착수할 수 있게 썼다. 배경·완료조건·금지사항이 모두 여기 있다.

---

## 0. 배경 (이것만 알면 된다)

큐브티를 **외부에 판매**한다. 고객사마다 **독립된 인스턴스**(별도 DB·컨테이너)를 설치하는 방식이다.
지금은 고객사 하나 받으면 컨테이너·DB·관리자·지점을 손으로 다 만들어야 해서 **반나절**이 걸린다.
이걸 **명령 한 줄**로 줄이는 게 이 작업의 목표다.

멀티테넌트로 바꾸는 게 아니다. **단일 테넌트 그대로, 인스턴스를 여러 개 띄우는 방식**이다.
(데이터가 물리적으로 분리되는 게 오히려 판매 포인트다 — 고객사 인사정보가 남의 DB에 섞이지 않는다.)

---

## 1. 이미 만들어져 있는 것 — `deploy/`

**새로 만들지 말 것.** 아래 4개가 이미 있고, 문법 검증까지 끝났다.

| 파일 | 역할 | 검증 상태 |
|---|---|---|
| `new-customer.sh` | 원커맨드 설치 | `bash -n` 통과 |
| `docker-compose.customer.yml` | 인스턴스용 compose | `docker compose config` 통과, 필수값 가드 동작 확인 |
| `init-tenant.js` | 빈 DB에 관리자 1명만 생성 | 인자검증·오류경로 실행 확인 |
| `README.md` | 설치·업데이트·백업·제거 절차 | — |

**설계 요건 (바꾸더라도 이건 유지)**

- compose 프로젝트명(`-p cubetee-<code>`)으로 인스턴스 격리 — 컨테이너·볼륨·DB 전부 분리
- 포트 파라미터화 (직영 3000, 고객사는 3101부터)
- `POSTGRES_PASSWORD`·`JWT_SECRET` 자동 생성, `.env`·접속정보는 권한 600
- 실패 시 자동 롤백 (만들다 만 컨테이너·볼륨 정리)
- **`prisma/seed.ts` 금지** — 개발용 더미(테스트 지점 3개 + 직원 50명)라 판매 설치에 쓰면 사고.
  반드시 `init-tenant.js`(관리자 1명만)를 쓴다
- 빈 DB이므로 `prisma db push` 사용. migrations 이력이 없는 프로젝트라 이게 맞다

## 2. 할 일

### A. 실제 설치 테스트 (먼저) — 운영 무관

문법만 검증됐고 **한 번도 실제로 돌려보지 않았다.** 이게 진짜 완료 조건이다.

1. 이미지 빌드 (`docker build -t cubetee:test .`)
2. 테스트 고객사 생성 — `--code testco --port 3199`
3. **브라우저로 로그인까지 확인**
4. 지점 등록 → 출퇴근 1건 → 휴가 신청 1건이 도는지 확인
5. `down -v` 로 정리

**막히는 지점이 나오면 스크립트를 고친다.** 그게 이 단계의 목적이다.

> 로컬(Windows) 이든 서버든 상관없다. 다만 서버에서 할 경우 **직영 3000 포트와 겹치지 않게** 할 것.

### B. `NEXT_PUBLIC_*` 런타임 전환 (그다음) — ⚠️ 운영 영향 있음

`NEXT_PUBLIC_*` 는 **빌드 시점에 코드로 박힌다.** 지금 구조면 고객사 도메인이 이미지에 구워져서
**고객사마다 이미지를 새로 빌드**해야 한다. 30곳이면 30번이다.

실제 사용처는 7곳뿐이고 **전부 서버 코드**라, 런타임 변수로 바꾸면 해결된다.

| 변수 | 위치 | 조치 |
|---|---|---|
| `NEXT_PUBLIC_APP_URL` (6) | `api/leave/[id]/approve` 138·269 · `api/contracts/[id]` 265 · `api/contracts/[id]/sign` 151·232 · `api/work/meetings/[id]/invite` 40 | → `APP_URL` |
| `NEXT_PUBLIC_API_URL` (1) | `lib/api-client.ts` 29 | → `API_URL` |
| `NEXT_PUBLIC_KAKAO_MAP_API_KEY` (2) | `lib/kakao-geocoding.ts` 22·75 | **그대로 둔다** (벤더 키, 고객사 공용) |

이후 `Dockerfile`의 `ARG/ENV NEXT_PUBLIC_APP_URL`·`NEXT_PUBLIC_API_URL` 제거,
루트 `docker-compose.yml`(직영)에 `APP_URL` 추가.

**위험 구간 — 링크 생성 4곳.** 잘못되면 알림 링크가 `localhost` 로 나간다. 배포 후 반드시 실물 확인:

- [ ] 휴가 결재 알림 링크
- [ ] 계약서 발송 메일 링크
- [ ] 계약 서명 링크
- [ ] 화상회의 초대 링크

### C. 운영 스키마 대조 (확인만)

운영 DB는 수동 DDL로 관리돼 왔다. `schema.prisma` 와 어긋나 있으면,
고객사는 `schema.prisma` 기준으로 만들어지므로 **"직영은 되는데 고객사는 안 되는" 버그**가 생긴다.

`prisma migrate diff` 로 한 번 대조하고 결과만 보고할 것. **운영 DB는 읽기만 한다.**

## 4. 하지 말 것

- **직영 운영에 영향 주는 변경을 임의로 하지 말 것.** B는 재배포가 필요하니 디렉터 확인 후 진행.
- `prisma/seed.ts` 를 판매 설치 경로에 끌어들이지 말 것.
- 운영 DB에 `db push` 금지 (기존 규칙 그대로). 새 고객사 빈 DB에만 쓴다.
- 멀티테넌트 전환을 시작하지 말 것. 지금은 단일 테넌트가 맞다. (40개 모델 + 146개 라우트 대공사)
- 기능 추가 금지. 이 작업은 **파는 데 필요한 것**만 한다.
